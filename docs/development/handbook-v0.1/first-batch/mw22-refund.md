## 目标与可见结果

1. 接通售后申请、后台审核、渠道执行（仅渠道支持时）、结果通知后的权益撤销，以及日账差异可查询处理。撤销必须走 MW20 同一账本：确认整笔退款成功后，只撤该订单来源（`sourceType=order`）的未用时长；退 A 不扣 B；已用完的 A 退款不追扣其他来源。按来源顺序消耗，不产生负数。账户摘要是派生值，禁止后台直接改 `expiresAt`。
2. 付款 / 发放 / 退款三套状态独立。只允许定义的迁移。平台最终退款成功才撤销权益；仅受理、处理中、失败都不扣。重复退款通知幂等，返回原结果。退款与发放乱序：退款先于发放则订单终局后不再开通；发放先于退款则只扣该来源未用余额。已退款订单晚到支付回调：记来源冲突并查单，不重新发放。
3. 首版商户操作提供整笔退款。非整笔 / 部分退款进入人工核对，不按猜测金额自动削天数。未知结果不重新建退款单。
4. `refund.request` 不直接承诺退款资格，不自动扣 VIP。重复请求关联原申请。operations 做 `refund.review`（建议，不能发起渠道退款）；super 做 `refund.execute`（绑定申请和金额，渠道支持时执行）。必须写原因。content 角色不得审退款、不得看过度订单明细。
5. Apple / iOS 订单：页面只给 App Store 申请指引，后台不出现不可执行的「商户直接退款」按钮。退款问询返回实际发货、开通和消耗证据；无证据时返回不确定结果，不编造使用记录以阻止退款。Android 与 iOS 同一会员写入同一 `vip_accounts`。Apple 现网验证留 MW29（Apple 不支持沙箱）。
6. 日账核对渠道成功交易、本地付款、发放及退款，差异列为可处理任务。对账发现的新成功交易走同一收据和发放幂等链路，不另写「直接加 VIP」快捷路径。`order.reconcile` 不修改金额。
7. 退款不删除合法完成的历史成绩、成长等级、勋章或历史解析。VIP 不加分、退款也不清空成长。
8. CloudBase 写入不把文档自带 `_id` 再 set 回去；新文档不依赖多集合事务里直接插入。
9. leftover 沿用 MW15 起独立核查：空清单或 `wroteDocs=false` 不得报 leftover=0。只删本轮入册的退款单 / 本轮测试订单与回执 / 本轮为退款准备的 order 来源账本与测试卷题答题；永不删种子十类、jobs / 审计 / 幂等、共享 `ranking_*` / `app_config`、历史成绩、会员账号、非本轮 gift 账本、MW21 非本轮套餐。

## 已裁定（本轮不重开）

1. 撤销走 MW20 同一账本，只撤 `sourceType=order` 的未用时长。
2. 三套状态独立；最终成功才撤；受理/处理中/失败不扣。
3. 整笔退款；部分转人工，不自动削天数。
4. `refund.request` 不承诺资格、不自动扣 VIP；重复关联原申请。
5. operations 只能 review；super 才能 execute；content 不能审、不能看过度订单明细。
6. Apple 无商户退款按钮；问询不编造使用记录。现网留 MW29。
7. 日账只列差异，不改金额；新成功交易走同一收据/发放幂等。
8. 退款不清空成长/成绩/勋章。
9. 无真实已付订单时用本轮测试夹具构造 order 来源账本与退款状态机：不得伪造渠道成功骗发放，不得写正式售价。T24「退 A 留 B」可用两笔 order 来源（或一笔 order + 一笔 gift）在账本上验证，不要求真机付款。
10. leftover 独立核查；空清单或 `wroteDocs=false` 不得 leftover=0。本轮 leftover=0 已核验。
11. 无事先 `refund.request` 时，`xpay_refund_notify` / `applyRefundChannelOutcome` 不得新建 `refunds` 文档。未知/受理/处理中只记冲突或日账差异。平台最终成功早于本系统申请：识别并处理该 order 未用时长，订单可标退款成功；随后 `refund.request` **补单**只绑定已发生结果（`state=succeeded`，`unknownResult=false`），不得走未知结果路径另建单。
12. 小程序订单页浏览/进页/`reload` 不自动 `markLeftoverOrderId`。只对用户主动点「记入本轮 leftover」的本轮测试订单入册。
