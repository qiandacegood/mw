# 思维工坊 CloudBase 支付与 VIP 技术方案 V1.0

日期：2026年10月3日  
依据：[产品 V1.1](../product/product-spec-v1.1.md)。本方案使用 CloudBase 承载订单、权益和回调服务，支付通道为微信小程序虚拟支付，不使用普通微信支付替代数字会员交易。

## 1 接入参数和边界

正式接入前需取得适用主体的 AppID、CloudBase 环境、虚拟支付资格、OfferID、商品标识、沙箱与现网配置，以及通知服务所需校验配置。CloudBase 环境 ID 不等于 AppID，也不等于支付商户或 OfferID。

前端只能获取本次收银台必要参数；AppKey、session_key、回调密钥与平台凭据仅服务端可见。测试环境配置和现网配置必须同时由环境白名单与订单 environment 字段约束，不允许客户端 env 参数选现网。

商品采用 VIP 天数直接购买，quantity 固定为 1。一个套餐版本对应已核对价格和时长的商品映射；已支付旧商品仍按旧订单履约。

微信官方当前虚拟支付文档覆盖多端路由，并规定 Apple 支付的开通及设备条件；实际以项目主体资格为准。iOS 不支持沙箱验证，Apple 退款由用户向 Apple 申请。[官方接入与退款说明](https://developers.weixin.qq.com/miniprogram/dev/platform-capabilities/business-capabilities/virtual-payment.html)

## 2 正常付款与发放

1. order.create 校验会员、计划版本、目标渠道与购买开关；冻结 planSnapshot、amountFen、durationSeconds、environment。服务端产生本地订单号及渠道业务号。
2. payment.prepare 接收一次性 wx.login code，服务端换取微信会话并核对 openId、AppID 与云调用上下文一致。会话短期加密保存，过期重新取得；不能把“云函数知道 openId”等同于已经取得支付签名所需 session_key。
3. 使用已冻结订单参数构造官方虚拟支付请求，客户端只调用收银台，不自己改金额或商品。官方签名算法和字段序列化通过 SDK 适配器集中处理，用官方测试向量验证。
4. 客户端返回只触发 order.refresh。mw-pay-hook 收到并校验平台通知，或服务端查单确认真实已付后，核对订单、用户、商品、金额、环境及交易号。
5. 一个小事务写 payment_receipts、orders.payState=paid，并创建唯一 grant job。已退款结果先到时直接进入核对，不排发放。
6. 发放事务锁定该会员 vip_accounts、源 order 与唯一 vip_grant，计算从实际发放时刻起的有效期，写账户摘要、来源及事件，订单置 granted。已存在对应有效 grant 则返回原结果。
7. 平台发货确认在权益持久成功后发送；通知重放只返回相同履约结论。本地已发放但平台确认失败时，任务只重发同一确认，不能再加天数。

不同订单同时付款通过同一会员账户文档串行化续期。记录真实 paidAt 与 grantedAt，发放迟到不能伪造付款时间，也不能让用户承担系统延迟造成的已购时长损失。

## 3 回调接入

mw-pay-hook 仅暴露必要路径，限制请求大小、方法及类型。先按虚拟支付订阅通知协议验证来源与消息完整性，再解析事件。保留验签所需原始字节，不能先格式化 JSON 或 XML；XML 解析关闭外部实体与外部网络访问。

虚拟支付事件不能机械套用普通微信支付 APIv3 的回调解密格式。接口适配器必须以真实配置的官方通知文档和测试报文为准，文档版本与验证样例在实现时留档。

通知成功响应代表已完成平台要求的处理。若业务可异步处理，先持久入 callback_events 与 jobs 再应答接收；对于要求确认发货完成的响应，只有权益成功持久化后才能确认发货。不能只写日志就回复已完成。

幂等层次：

| 层次 | 防重依据 |
| --- | --- |
| 通知接收 | 稳定事件标识或规范化业务事件键 |
| 付款确认 | provider、environment、transactionId 唯一 |
| 权益发放 | orderId 唯一来源 |
| 退款申请 | refundId 及渠道退款业务号 |
| 权益撤销 | refundId 关联目标 grant 与唯一事件 |

验签失败直接拒绝，不创建订单或发放任务。金额、用户或商品不匹配进入 needsReview，日志只记录内部 ID、摘要和错误码，不记录完整会话或密钥。

## 4 结果未知与补偿

付款状态 pending、confirming、paid、closed；权益状态 pending、processing、granted、error、revokedRemaining；退款状态 none、requested、processing、succeeded、failed。只允许定义的状态迁移，晚到 pending 通知不能把 paid 改回未支付。

客户端取消不能作为支付失败终态。超时、网络中断、平台回调缺失均查同一业务号。待支付订单目标过期 15 分钟；真正关闭前查单并取得渠道关单结果。关单与付款竞争时尊重真实已付状态。

首版外部 HTTP 单次目标超时 3 秒，一次用户请求最多一次主动查单；失败转持久补偿，不在 15 秒函数内连续叠加无限重试。后台任务采用带抖动的退避，例如 1、2、5、15 分钟，仍未知的订单进入人工队列继续保留；实际频率必须符合平台限额。

每日对账核对渠道成功交易、本地付款、发放及退款，差异列为可处理任务。对账发现的新成功交易也走同一收据和发放幂等链路，不另写“直接加 VIP”快捷路径。

## 5 权益账本与退款并发

vip_grants 保留来源、发放秒数、已消耗秒数、剩余秒数和顺序。账户摘要仅为快速判权派生值；后台不能直接改 expiresAt 取代账本。

发放或退款时先推进本会员已消耗时间；按来源顺序消耗，不产生负数。确认整笔退款成功后，把该来源剩余时长撤销，其余来源不减，重新顺接有效期。已经消耗的时间不向其他订单追扣。

退款先于发放：订单标记终局，发放事务复核后不再开通。  
发放先于退款：按目标来源扣未用余额。  
退款通知重复：唯一退款事件已存在则返回原结果。  
退款失败或仅已受理：不撤销权益。  
非整笔退款：记录真实金额并进入人工核对，不猜测天数比例。  
已退款订单晚到支付回调：记录来源冲突并查单，不重新发放。

账户历史较多时先在事务外读取分页记录，事务内校验账户 revision 与输入摘要再应用；超出事务上限采用账户专属分批重建任务。重建期间同账户新发放排队，外部付款仍可确认，界面准确显示开通处理中。

## 6 Apple 订单

用户订单页面显示与渠道匹配的售后说明，不给 Apple 订单显示“商户直接退款”按钮。退款问询返回实际发货、开通和消耗证据，最终成功通知才触发撤销。无证据时返回符合官方协议的不确定结果，不编造使用记录以阻止退款。

Android 和 iOS 同一会员的权益写入同一 vip_accounts，换设备不会重新发放。渠道商品与金额可能有配置差异，售价是否保持一致属于上线商品配置，不能在客户端私自换算。

Apple 现网验证必须在主体、商品、环境和小额金额获明确授权后执行；本次技术文档授权不等于授权扣款。未完成现网验证不能宣称首版两端支付已经验收通过。

## 7 必测异常

至少验证：伪造成功返回、金额修改、越权订单、重复点击、同通知十次重放、两个不同订单并发付款、发放后通知确认失败、先退款后发货、两个退款工作器并发、VIP 当前有效及已到期续费、后台误赠撤销、查单长期未知、沙箱回调攻击现网、AppID 不匹配、会话 code 重复使用。

验收对应[测试计划](../testing/acceptance-plan-v1.0.md)。本方案没有声称已拿到真实账号资料或已发起交易。
